DLL loading, ownership, and banking

Handle missing disk files, share dependencies, preserve state, and use RAM under ROM.

Decide when disk I/O happens

Start with an explicit load while you bring up a new module. Preload moves disk I/O to startup. On-demand moves it to the first call that needs the module. Choose based on where the user can tolerate a delay and what your program will do if the disk entry is missing.

Preload before main

Current module · configuration excerpt
current {
    load = .preload;
    load_file = "enemyrt";
}

Load on the first call

Current module · configuration excerpt
current {
    load = .on_demand;
    load_file = "enemyrt";
}

Both are settings inside module_loader. Supply disk staging and a filename. For dependencies, put the policy on the dependency row and supply its file. With .manual, use an explicit load or acquire. With .preload, check availability at entry before relying on the export. With .on_demand, handle null at the call site. A later call to an already loaded module can reuse the cache.

Keep a module callable while callers still need it

Loading establishes residency and its initial reference. Repeating an ensure-load leaves the reference count alone. For a dependency, a successful acquire() or acquireGraph() takes a reference, including when the payload is already loaded. Pair those calls with release() or releaseGraph(). Releasing the final reference clears callability. This is separate from a window swap, which can displace a DLL while its references and cached payload remain valid.

Two owners take references

Typed graph ownership fixture · excerpt
test6502.expectEqualBool(1, true, MathCore.acquireGraph());
test6502.expectEqualBool(2, true, MathCore.acquireGraph());
MathCore.releaseGraph();
// MathCore still has an owner.

The last owner releases

Typed graph ownership fixture · excerpt
MathCore.releaseGraph();
test6502.expectEqualBool(7, false, ZeroPage.module.isLoaded("math_core"));
test6502.expectNull(8, MathCore.add(3));

The fixture calls the module between the two releases and gets a value. After the final release it gets null, even though bytes may remain in the REU and window. It then acquires the graph again and calls successfully. These test6502 statements are assertions for the host runner. Load prerequisites and recover from a failed graph load

Declare graph edges with requires on each participating row, including an empty list for a leaf. The compiler checks missing nodes and cycles. The loader visits prerequisites first. On failure it rolls back rows or references introduced by that operation. A dependency row can opt into the graph path with graph = true under preload or on-demand policy.

Declare a graph policy

Dependency row · configuration excerpt
dependency math_core {
    file = "mathcore";
    load = .on_demand;
    graph = true;
    requires = .{.fixed_math};
}

dependency fixed_math {
    file = "fixedmath";
    requires = .{};
}

Check a missing dependency

Host fixture · assertions
test6502.expectNull(2, MathCore.add(3));
test6502.expectEqualBool(3, false, ZeroPage.module.isLoaded("math_core"));
test6502.expectEqualBool(4, false, ZeroPage.module.isLoaded("fixed_math"));

Loading a graph makes its modules available in REU. It does not invoke their exports. To call a transitive module such as FixedMath, declare its binding and provide its sidecars at build time. A typed transitive binding can call its exports after a direct dependency loads the graph. It cannot independently acquire that transitive graph through the same binding.

Choose a visible window or RAM under ROM

A visible RAM window is the easiest place to start. If you need more visible RAM for the main program, put the window under BASIC or KERNAL ROM. The range must fit entirely within the selected bank. The loader restores the processor port after the banked operation.

Under BASIC ROM

Region inside memory
region module_window: c64 at 0xa000 size 0x0800
    bank .ram_under_basic;

Under KERNAL ROM

Region inside memory
region module_window: c64 at 0xe000 size 0x0800
    bank .ram_under_kernal;

The KERNAL path also preserves processor status and masks IRQs while KERNAL is hidden. Keep these exports independent of KERNAL services. ZeroPage supports a resident trampoline for supported console calls. Keyboard, raw KERNAL, disk, and unsupported inline assembly paths are rejected for this bank. Use a visible window when the export needs those services.

Choose which state survives activation

When a new DLL takes a window, the loader copies a fresh image over the old contents. Use persist_in_reu for selected state bytes that must survive. The state offset is relative to the start of the execution window. For state at $c100 in a $c000 window, the offset is $0100. Use discard_on_unload when an unload should discard that row's state. These policies are mutually exclusive for a row.

Keep two bytes across activations · configuration excerpt
current {
    persist_in_reu at 0x0100 size 2;
}

Persistent ranges are saved separately from the payload before replacement or final unload and restored after copy and relocation. They consume REU capacity. The compiler checks bounds, overlap, and available cache space. Write two bytes, unload, clear the window, and reload · State and cache reservations

Know which file goes where

FileWho uses it
.zpmod.jsonCaller build and inspection. Describes ids, ABI, export signatures and ordinals.
.zpmod.relocsim.jsonCaller build and inspection. Records the relocation plan and its simulation.
.zpmodHost tooling. Versioned binary with metadata and payload.
.zpmod.disk.prgC64 disk loader. Put it on the D64 under the declared disk filename.
.zpmod.diskmanifest.jsonDisk packaging, when configured. Describes filenames and payload placement.

Exports are ordered from zero. The payload begins with one three-byte JMP per export, so dispatch uses window_base + ordinal * 3. The compiler emits relocation records for known addresses, including full 16-bit operands and separate low and high bytes. The target uses compiled rows and ordinals. It reads the disk payload without parsing the build sidecars. Read-only data relocation demo · Format and relocation details

Tell a build error from an unavailable call

What you seeWhat to check
Binding signature rejectedMatch the export name, argument types, and return type. Rebuild stale sidecars. Signature mismatch fixture
Graph or placement rejectedCheck graph rows and edges, window visibility, reserved ranges, and REU capacity. Cycle fixture · Cache sizing fixture
load fails or the call returns nullCheck REU setup, the disk entry, and whether the row is still loaded. In manual mode, ensure the load succeeded before calling. Call before loading fixture

Declare your binding in the caller and call it from a supported static-frame context. DLL export implementations use the software-stack convention. The compiler rejects unsupported loader calls within software-stack functions. The standalone fixed-address cache described here also differs from the proposed ReadyOS host-managed cache.

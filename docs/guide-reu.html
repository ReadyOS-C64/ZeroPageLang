Far data and materialized views

Transfer bytes, fetch typed records, or edit a working range in C64 RAM and flush it.

Move, compare, fill, and swap bytes

A C64 pointer addresses the CPU's 64 KiB address space. A far address names a byte in the REU. The REU controller moves bytes between the two spaces using DMA. The CPU can then read the copied bytes in ordinary C64 RAM.

Use ZeroPage.reu.present() before a transfer on a machine where the REU may be absent. Configure the emulator with a 16 MiB REU for the examples in this guide. On hardware, check that every configured range fits the installed capacity. Presence alone gives no capacity guarantee.

CallWhat changes
copyC64ToReu(c64_addr, reu_addr, len)The REU receives the bytes.
copyReuToC64(reu_addr, c64_addr, len)The C64 destination receives the bytes.
compare(c64_addr, reu_addr, len)Returns whether the ranges match. Both ranges keep their contents.
fill(reu_addr, value, len)Writes the same byte into every position in the REU range.
swap(c64_addr, reu_addr, len)Exchanges the contents of both ranges.

The raw far address is a compile-time value from 0x000000 to 0x00ffffff. The C64 address and byte count accept supported runtime expressions. Supply a nonzero byte count. The REU interprets a zero count as a 64 KiB transfer. The compiler rejects a literal zero. Check a runtime count before issuing DMA.

reu-transfer.zp64
const c64 = @import("c64");
const ZeroPage = @import("ZeroPage");

memory {
    region scratch_reu: reu at 0x010000 size 16;
}

export fn main() void {
    c64.console.clear();
    if (ZeroPage.reu.present() == true) {
        const source: [*]volatile u8 = @ptrFromInt(0x0500);
        const result: [*]volatile u8 = @ptrFromInt(0x0528);
        source[0] = 0x11;
        source[1] = 0x22;

        ZeroPage.reu.copyC64ToReu(0x0500, 0x010000, 2);
        ZeroPage.reu.copyReuToC64(0x010000, 0x0528, 2);
        if (ZeroPage.reu.compare(0x0528, 0x010000, 2)) {
            ZeroPage.reu.fill(0x010000, 0x55, 2);
            ZeroPage.reu.swap(0x0528, 0x010000, 2);
            if (result[0] == 0x55 and result[1] == 0x55 and
                ZeroPage.reu.compare(0x0500, 0x010000, 2))
            {
                c64.console.print("REU TRANSFER OK\n", .{});
                c64.vic.border = 5;
            } else {
                c64.console.print("REU SWAP FAILED\n", .{});
                c64.vic.border = 2;
            }
        } else {
            c64.console.print("REU COPY FAILED\n", .{});
            c64.vic.border = 2;
        }
    } else {
        c64.console.print("ENABLE AN REU\n", .{});
        c64.vic.border = 2;
    }
}

Allocate far bytes without choosing an address at each call

A far arena carves allocations out of a named REU region. A successful allocation gives you a FarBytes handle. The handle identifies the allocation and carries its length. Use copyFromC64 and copyToC64 to move bytes using the handle's base address. Keep the transfer length within the allocation and the C64 buffer. The copy still takes an explicit byte count.

From the far arena demo
const maybe_far = assets.allocBytes(2);
if (maybe_far) |far| {
    ZeroPage.reu.copyFromC64(far, 0x0500, 2);
    ZeroPage.reu.copyToC64(far, 0x0528, 2);
}

The first argument stays far in both handle-based operations. Read the verbs from the handle's point of view: copyFromC64 writes the handle's range, and copyToC64 reads it. When the arena is exhausted, allocation returns null. Reset reclaims the entire arena. Finish using its handles and views before resetting. There is no per-allocation free for a far arena.

Use this approach for raw data such as a tile map or a collection of fixed-size blocks. Use a typed view when you need to read and replace individual records. Complete far arena copy demo · Exhaustion, reset, and independent arenas · Rejected far pointer dereference

Allocate and update rich records

Allocate @sizeOf(Enemy) * count bytes and bind the handle to the record type and a compile-time count with ZeroPage.reu.view. Initialize the records you plan to read. The view supports 1–255 records of 1–255 bytes each. view.len reports the number of records. The compiler checks literal indexes. Keep runtime get and set indexes within the view yourself.

The example stores nested coordinates, a word score, an enum, and a fixed patrol array. A typed get or set transfers one record through compiler-owned staging. Supported layouts include scalar and enum fields, nested records, and fixed scalar or enum arrays. Pointer, optional, union, string, and array-of-record fields are outside the far-record subset.

reu-records.zp64
const c64 = @import("c64");
const ZeroPage = @import("ZeroPage");

const Team = enum(u8) { red = 1, blue = 2 };
const Position = struct { x: u8, y: u8 };
const Enemy = struct {
    hp: u8,
    score: u16,
    team: Team,
    pos: Position,
    patrol: [2]u8,
};

memory {
    region work_ram: c64 at 0x9000 size 0x0010;
    region asset_ram: reu at 0x010000 size 0x0100;
    arena scratch in work_ram;
    arena assets in asset_ram;
}

export fn main() void {
    c64.console.clear();
    if (assets.allocBytes(@sizeOf(Enemy) * 3)) |far| {
        var enemies = ZeroPage.reu.view(Enemy, far, 3);
        enemies.set(1, Enemy{
            .hp = 9,
            .score = 0x1200,
            .team = .blue,
            .pos = Position{ .x = 12, .y = 3 },
            .patrol = [_]u8{ 4, 8 },
        });
        enemies.set(2, Enemy{
            .hp = 4,
            .score = 0x2300,
            .team = .red,
            .pos = Position{ .x = 6, .y = 7 },
            .patrol = [_]u8{ 2, 5 },
        });

        if (enemies.materializeRange(scratch, 1, 2)) |local| {
            var enemy = local.get(0);
            enemy.hp -= 2;
            enemy.score += 1;
            local.set(0, enemy);
            enemies.flushRange(1, local);
            scratch.reset();

            const saved = enemies.get(1);
            const untouched = enemies.get(2);
            if (saved.hp == 7 and saved.score == 0x1201 and saved.team == .blue and
                saved.pos.x == 12 and saved.patrol[1] == 8 and untouched.score == 0x2300)
            {
                c64.console.print("REU RECORDS OK\n", .{});
                c64.vic.border = 5;
            }
        }
    }
    assets.reset();
}

Materialize, edit, flush, reset

  1. materializeRange(scratch, 1, 2) reserves space in a named near arena and copies far indexes 1 and 2 into local indexes 0 and 1. The range count is a compile-time literal. A supported runtime start is allowed.
  2. local.get and local.set access C64 RAM. Edits to the near view leave the far records unchanged until a flush.
  3. flushRange(1, local) writes the local range back starting at far index 1. Reset the near arena only after the final flush and after you are done with all its live views.
  4. Check results with a fresh far get. Reset the far arena when its handles are no longer needed.

When the whole table fits in C64 RAM, materialize(scratch) and flush(local) move all records at once. Whole-view flush requires a near view of the same record type and count. Range flush uses the near view's count and the supplied far start. For a runtime start, preserve the value that succeeded during materialization. The flush emitter checks literal starts, so your code must keep a runtime destination in bounds.

Materialization needs a named near arena and the static-frame subset. Copying a range once can avoid a DMA setup for each record access in a loop. The tradeoff is temporary C64 RAM and the cost of copying every record in the range. If you only read one record, a far get keeps that working memory small. If you make no edits, skip the write-back and reset the arena when the near view is no longer needed.

38_far_reu_materialize_flush.zp64
const c64 = @import("c64");
const ZeroPage = @import("ZeroPage");

const Enemy = struct {
    hp: u8,
    x: u8,
    score: u16,
};

memory {
    region main_ram: c64 at 0x9000 size 32;
    region assets_ram: reu at 0x010000 size 0x0100;

    arena near_heap in main_ram;
    arena assets in assets_ram;
}

export fn main() void {
    c64.console.clear();
    c64.console.print("FAR MATERIALIZE\n", .{});

    const maybe_far = assets.allocBytes(@sizeOf(Enemy) * 2);
    if (maybe_far) |far| {
        var enemies = ZeroPage.reu.view(Enemy, far, 2);
        enemies.set(0, Enemy{ .hp = 3, .x = 4, .score = 0x1234 });
        enemies.set(1, Enemy{ .hp = 5, .x = 6, .score = 0x3456 });

        if (enemies.materialize(near_heap)) |local| {
            const enemy = local.get(0);
            local.set(0, Enemy{ .hp = enemy.hp + 2, .x = enemy.x + 2, .score = enemy.score + 1 });
            enemies.flush(local);
            near_heap.reset();
        }

        const loaded = enemies.get(0);
        if (loaded.hp == 5 and loaded.x == 6 and loaded.score == 0x1235) {
            c64.console.print("FLUSH OK\n", .{});
            c64.vic.border = 5;
        } else {
            c64.console.print("FLUSH BAD\n", .{});
            c64.vic.border = 2;
        }
    } else {
        c64.console.print("FAR ALLOC BAD\n", .{});
        c64.vic.border = 2;
    }
}

Handle a range that does not fit

A literal range outside the far view is a build error. With a runtime start, a range beyond the view returns null. Running out of space in the near arena also returns null. Keep the success capture around any editing and flush operations. The host fixture distinguishes the two failures by first testing a bad runtime start, then requesting a valid range after consuming the arena's space.

Runtime range and exhaustion assertions
var bad_start: u8 = 5;
const bad = enemies.materializeRange(near_heap, bad_start, 2);
test6502.expectNull(11, bad);

const oom = enemies.materializeRange(near_heap, 0, 2);
test6502.expectNull(12, oom);

Match the source view to the destination

Whole-view flush requires the same record type and count on both sides. A local view of one Enemy cannot stand in for a far table of two Enemy records. To update just the first record, use two.flushRange(0, local) with that one-record local view. The local count determines the number of records written.

Rejected whole-view flush · excerpt from the count fixture
if (one.materialize("main")) |local| {
    two.flush(local);
}

Both forms require the matching record type. Equal byte widths alone give no conversion between types. If you are migrating a record format, read the old fields, construct a new record explicitly, and write it through the new view. When troubleshooting, check type, count, and destination start before looking at DMA or banking.

Process a table larger than its C64 working space

Four three-byte sectors occupy twelve bytes in REU. The C64 scratch arena has six bytes, enough for two sectors. Process starts 0 and 2 in sequence. For each range, bring in both records, run three update passes in C64 RAM, and write back once. The same arena serves the next range after reset. This works because the first near view has gone out of use before the second allocation.

reu-working-set.zp64
const c64 = @import("c64");
const ZeroPage = @import("ZeroPage");

const Sector = struct { visits: u8, score: u16 };

memory {
    region work_ram: c64 at 0x9000 size 6;
    region asset_ram: reu at 0x010000 size 0x0100;
    arena scratch in work_ram;
    arena assets in asset_ram;
}

fn update(sector: Sector, bonus: u8) Sector {
    return Sector{
        .visits = sector.visits + 1,
        .score = sector.score + @as(u16, bonus),
    };
}

fn run() bool {
    if (ZeroPage.reu.present() == false) {
        return false;
    }
    if (assets.allocBytes(@sizeOf(Sector) * 4)) |storage| {
        var sectors = ZeroPage.reu.view(Sector, storage, 4);
        sectors.set(0, Sector{ .visits = 0, .score = 0x1000 });
        sectors.set(1, Sector{ .visits = 0, .score = 0x2000 });
        sectors.set(2, Sector{ .visits = 0, .score = 0x3000 });
        sectors.set(3, Sector{ .visits = 0, .score = 0x4000 });

        var start: u8 = 0;
        while (start < 4) {
            if (sectors.materializeRange(scratch, start, 2)) |local| {
                var pass: u8 = 0;
                while (pass < 3) {
                    const a = local.get(0);
                    const b = local.get(1);
                    const updated_a = update(a, 1);
                    const updated_b = update(b, 2);
                    local.set(0, updated_a);
                    local.set(1, updated_b);
                    pass += 1;
                }
                sectors.flushRange(start, local);
            } else {
                assets.reset();
                return false;
            }
            scratch.reset();
            start += 2;
        }

        const first = sectors.get(0);
        const second = sectors.get(1);
        const third = sectors.get(2);
        const last = sectors.get(3);
        assets.reset();
        return first.visits == 3 and first.score == 0x1003 and
            second.visits == 3 and second.score == 0x2006 and
            third.visits == 3 and third.score == 0x3003 and
            last.visits == 3 and last.score == 0x4006;
    }
    return false;
}

export fn main() void {
    c64.console.clear();
    if (run()) {
        c64.console.print("WORKING SET OK\n", .{});
        c64.vic.border = 5;
    } else {
        c64.console.print("WORKING SET FAILED\n", .{});
        c64.vic.border = 2;
    }
}

Compare repeated far updates with a working copy

The same four sectors can be updated directly in REU. This variant keeps the same initial data, the same three passes over each pair, and the same final checks. Each pass reads and writes both far records. In the materialized version, each pair crosses the bus once in each direction and the passes access C64 RAM.

Direct far updates · excerpt
var start: u8 = 0;
while (start < 4) {
    var pass: u8 = 0;
    while (pass < 3) {
        const a = sectors.get(start);
        const b = sectors.get(start + 1);
        const updated_a = update(a, 1);
        const updated_b = update(b, 2);
        sectors.set(start, updated_a);
        sectors.set(start + 1, updated_b);
        pass += 1;
    }
    start += 2;
}

When each record needs one update, copying it into a separate arena adds another representation to manage and may offer little benefit. With repeated accesses, the savings grow with the passes you can keep local. Count the transfers and working RAM first, then time the actual path.

DLLs, caches, and activation

Package disk payloads, seed the cache from a resident image, and reactivate a cached module.

Disk, REU cache, and execution window

A module's source payload, cache slot, and active window are separate. An embedded current module seeds its REU slot from bytes in the resident PRG. A disk load reads a disk PRG into staging RAM and seeds the slot from there. Activation copies cached bytes into a C64 execution window, applies relocations, and restores any configured state. The CPU calls through the window's jump table.

OperationWhere bytes moveWhat changes
Embedded current load()Resident PRG → REU → windowFirst load seeds the current row
loadFromDisk()Disk → C64 staging → REU → windowA disk payload seeds the row
Call a loaded, displaced rowREU → its C64 windowWindow owner changes, relocation and state restore run
Call the active rowDispatch through the current windowOrdinal selects the export
Final releaseOptional state snapshot to REUThe row loses callability even if bytes remain

The .zpmod.json and .zpmod sidecars describe module id, ABI, export order, sections, and relocation information. Disk packaging uses the disk PRG payload. The runtime works with compiler-generated rows and ordinals. Module ABI and sidecar format

Declare the export signature and call it

module … abi 1 declares the producer and its exports. The extern module declaration gives the caller a local binding name and the export signatures it uses. The compiler checks a current-module binding against its source exports and a dependency binding against its build-time sidecars. Calls resolve to a module row and export ordinal at build time.

The prototype declares the export's payload type. A call to a u8 export produces ?u8 because a known signature does not guarantee runtime availability. The string-based ZeroPage.module.call API also resolves names at compile time. The typed form makes normal dotted calls and signatures visible in source. Module API reference

Seed an REU cache without disk I/O

The named-region example has an execution window at $c000, a cache at REU $030000, and a software stack at $c800. It declares no disk staging region. RegionDll.load() seeds the current module from the PRG. The typed call RegionDll.tick(5) returns ?u8: a successful dispatch yields 6, and an unavailable module yields null.

96_memory_regions_dll.zp64
const c64 = @import("c64");
extern module RegionDll = region_dll {
    fn tick(value: u8) u8;
}

memory {
    region near_arena: c64 at 0x9000 size 0x0100;
    region module_window: c64 at 0xc000 size 0x0800;
    region software_stack: c64 at 0xc800 size 0x0400;
    region module_cache: reu at 0x030000 size 0x010000;

    stack in software_stack;
    arena near_heap in near_arena;
}

module_loader {
    window main in module_window;
    reu_cache in module_cache;
}

module region_dll abi 1 {
    export tick;
}

fn tick(value: u8) callconv(.stack) u8 {
    return value + 1;
}

export fn main() void {
    c64.console.clear();
    c64.console.print("REGION ARENA DLL\n", .{});

    var ok = false;
    const allocation = near_heap.allocBytes(2);
    if (allocation) |bytes| {
        bytes[0] = 0x55;
        bytes[1] = 0xaa;
        if (RegionDll.load()) {
            if (RegionDll.tick(5)) |value| {
                ok = value == 6;
            }
        }
    }

    if (ok) {
        c64.console.print("REGION DLL CACHE OK\n", .{});
        c64.vic.border = 5;
    } else {
        c64.console.print("REGION DLL FAILED\n", .{});
        c64.vic.border = 2;
    }
}

Package and seed from disk

The typed current-module demo first loads its embedded module, then unloads it and checks that the call returns null. EnemyRuntime.loadFromDisk("enemyrt") reloads the row from disk. The same typed call EnemyRuntime.border(3) then succeeds. The filename is a disk entry, while the export name and signature come from the binding.

64_module_typed_current_binding.zp64
const c64 = @import("c64");

extern module EnemyRuntime = enemy_runtime {
    fn border(value: u8) u8;
}

memory {
    region call_stack: c64 at 0xc800 size 0x0400;
    region module_window: c64 at 0xc000 size 0x0800;
    region module_cache: reu at 0x030000 size 0x010000;
    region staging_ram: c64 at 0x9000 size 0x0800;

    stack in call_stack;
}

module_loader {
    window main in module_window;
    reu_cache in module_cache;
    disk_staging in staging_ram;
}

module enemy_runtime abi 1 {
    export border = borderColor;
}

fn borderColor(seed: u8) callconv(.stack) u8 {
    return seed + 2;
}

export fn main() void {
    c64.console.clear();
    c64.console.print("MODULE TYPED CURRENT\n", .{});
    if (EnemyRuntime.load()) {
        EnemyRuntime.unload();
        if (EnemyRuntime.border(3) == null) {
            if (EnemyRuntime.loadFromDisk("enemyrt")) {
                const maybe_border = EnemyRuntime.border(3);
                if (maybe_border) |border| {
                    c64.console.print("TYPED CURRENT OK\n", .{});
                    c64.vic.border = border;
                } else {
                    c64.console.print("TYPED CALL FAIL\n", .{});
                    c64.vic.border = 2;
                }
            } else {
                c64.console.print("TYPED DISK FAIL\n", .{});
                c64.vic.border = 2;
            }
        } else {
            c64.console.print("TYPED UNLOAD FAIL\n", .{});
            c64.vic.border = 2;
        }
    } else {
        c64.console.print("TYPED LOAD FAIL\n", .{});
        c64.vic.border = 2;
    }
}

Swap two cached modules through one window

The typed multi-window example assigns both MathCore and FixedMath to aux. The first graph acquire loads both payloads into separate REU slots. A call to MathCore.add activates MathCore. A call to FixedMath.bias replaces it in the aux window. The next call to MathCore.add restores MathCore from its REU cache slot without fetching it from disk again.

The actual demo writes two bytes at window offset $0400 before switching. Its persist_in_reu declaration saves those bytes in a separate snapshot slot and restores them after reactivation. The later final release clears callability. Reacquiring the graph is a new load operation, separate from the earlier cache hit.

Typed dependency calls · excerpt
if (MathCore.acquireGraph()) {
    if (MathCore.add(3)) |first| {
        if (FixedMath.bias(4)) |second| {
            if (MathCore.add(4)) |reactivated| {
                // MathCore is active again. first = 5, second = 7, reactivated = 6.
            }
        }
    }
    MathCore.releaseGraph();
}

Choose loading, ownership, and banking policies

Manual loading gives the program explicit control. Preload fetches configured rows at entry. On-demand loading runs at a configured call site. The graph form loads prerequisites in topological order and rolls back changes from a failed operation. load ensures residency, while acquire adds an ownership reference. Release the matching ownership when done. A call returns an optional because a row can be unavailable.

A window may use visible RAM, RAM under BASIC, or RAM under KERNAL. Banked activation saves and restores the processor port. The KERNAL path masks interrupts during hidden-ROM work and restricts what an export can call. Use additional windows when keeping two modules active at once is worth the RAM. For a window shared by multiple rows, use an explicit state policy for bytes that must survive replacement.

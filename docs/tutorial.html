ZeroPage introduction

Read a first program, then follow the language into the C64 hardware and memory model. Install and build when you are ready to run the examples.

Read your first program

The compiler starts at export fn main() void. The c64 import provides the machine-facing API. .{} is an empty argument tuple for the formatter.

hello.zp64
const c64 = @import("c64");

export fn main() void {
    c64.console.clear();
    c64.console.print("HELLO FROM ZEROPAGE\n", .{});
    c64.vic.border = 5;
}
Show commands
Terminal
mkdir -p build
./zig-out/bin/zp64c compile examples/hello.zp64 -o build/hello.prg
x64sc -autostart build/hello.prg

The default image loads at $0801. A BASIC line runs SYS 2061, entering the compiled program at $080d. Expect a greeting and a green border. On hardware, put the PRG on a disk or compatible storage device, load it, and enter RUN.

Write typed 6510 code

Save the example as tutorial-colors.zp64 in the repository root. Each keypress advances to the next color. Return exits the program.

tutorial-colors.zp64
const c64 = @import("c64");

const colors = [_]u8{ 2, 5, 6 };

fn nextIndex(index: u8) u8 {
    if (index == 2) {
        return 0;
    }
    return index + 1;
}

export fn main() void {
    var index: u8 = 0;
    c64.console.clear();
    c64.vic.border = colors[index];
    c64.screen.hexAt(0, 0, index);
    var pressed = c64.keyboard.waitPetscii();
    while (pressed != c64.key.return_) {
        index = nextIndex(index);
        c64.vic.border = colors[index];
        c64.screen.hexAt(0, 0, index);
        pressed = c64.keyboard.waitPetscii();
    }
}
Show commands
Terminal
./zig-out/bin/zp64c compile tutorial-colors.zp64 -o build/tutorial-colors.prg
x64sc -autostart build/tutorial-colors.prg

The fixed array has three bytes. nextIndex keeps the runtime index within bounds because generated indexing has no runtime bounds check. Use u8 for byte values and u16 or usize for words and addresses. Types, control flow, and language limits

Talk to the hardware

The border helper maps to the VIC-II register at $d020. The example below uses a volatile pointer to that register, then an assembly block to write the background register at $d021. Save it as tutorial-hardware.zp64 and compile it using the same command pattern.

tutorial-hardware.zp64
export fn main() void {
    const border: *volatile u8 = @ptrFromInt(0xd020);
    border.* = 5;
    asm {
        lda #$06
        sta $d021
    }
}

Use c64.screen for direct screen writes, c64.console for PETSCII output and formatting, and c64.kernal when you need the ROM routines. The keyboard API reports PETSCII values. Inline assembly has a documented instruction and operand subset. C64 API · Inline assembly rules

Plan the memory layout

Open the memory placement demo. It declares visible code at $2000, an arena at $9000, and a region at $e000 behind KERNAL ROM. The resident image starts from its configured entry at $1000.

95_memory_regions_placement.zp64 · placement excerpt
const c64 = @import("c64");

const hidden_values linksection("hidden") = [_]u8{ 0x21, 0x42, 0x63 };

memory {
    region direct_code: c64 at 0x2000 size 0x0100;
    region near_arena: c64 at 0x9000 size 0x0100;
    region hidden_code: c64 at 0xe000 size 0x0100 bank .ram_under_kernal;

    placement direct in direct_code;
    placement hidden in hidden_code load .startup_copy;
    arena near_heap in near_arena;

    image prg {
        load_addr = 0x0801;
        entry_addr = 0x1000;
        basic_stub = true;
        address_limit = 0xc600;
    }
}

fn directAdd(value: u8) linksection("direct") u8 {
    return value + 1;
}

fn hiddenLookup(index: u8) linksection("hidden") u8 {
    return hidden_values[index];
}

linksection("hidden") places the lookup function and table together. .startup_copy keeps their bytes in the load image and copies them to the run address before main. A resident call gateway exposes the hidden RAM and restores the previous mapping. The demo also uses near_heap.allocBytes(2), which returns an optional pointer to visible C64 RAM.

Expect PLACEMENT ARENA OK. Open build/placement.prg.zpmap.json and compare the load and run addresses of the hidden placement. A named pool allocates equal-sized blocks, while an arena releases its allocations together with reset(). The separate zero_page policy governs borrowed bytes and fixed reservations.
